### Reproduction recipe for R01–R04

Use the existing synthetic corpus in `tests/scvia/fixtures/ml/synthetic.py` and the minimal release writer in `tests/scvia/unit/test_release.py`. All output roots must be temporary.

1. Create and validate a minimal release; then create `release/site/index.html` and `release/site/private.json`. Revalidate and publish into a temporary `LocalDirectoryDestination`. Current behavior: PASS and both unchecked files become active.
2. Train a synthetic baseline bundle with `train_cutoff=2025-01-01`, `calibration_end=2025-04-01`, `holdout_end=2026-01-01`, `target_seasons_from=2023`, `candidates=()`, two folds and one thread. Request replay at `2024-03-01T00:00:00Z` for season 2024 stage `r01`. Current behavior: available/scored, without a temporal model rejection.
3. Set that training config's `feature_spec.window_long=2`; forecast the fixture's future 2026 targets. Compare returned features to `build_features(history, artifact.features.keys, original_spec)`. Current behavior: inference uses default 5.
4. Replace the first fixture player-game's `available_at` with `2026-02-01T00:00:00Z`. Build 2025 historical features from a new History instance. Current behavior: season-order exception.

## Legacy risks still relevant to replacement design

The earlier audit contains detailed source references. The current review also inspected the affected prediction, scraper, shell and workflow code. These must remain in scope even though the prototype has improved individual modules.

| ID | Priority / area | Existing behavior | Replacement requirement |
|---|---|---|---|
| L01 | P0 / modeling | Historical feature rows can acquire next-round forecast filenames; player-group validation and preprocessing do not establish future-game accuracy | Explicit fixture targets, time-ordered folds, fold-local preprocessing and separate prospective/replay archives |
| L02 | P0 / identity | Name/team joins, inferred dates, inconsistent finals codes and duplicate player files can change populations | Stable identities, period-aware registries, explicit time quality and quarantine |
| L03 | P0 / refresh | Empty fetch/parse results and caught worker exceptions can appear as a successful refresh | Typed PASS/FAIL/UNKNOWN, required-work accounting, unchanged accepted pointer on failure |
| L04 | P1 / refresh | Last-date/last-counter cutoffs miss interior gaps and unchanged-row corrections | Source-key reconciliation, correction overlap, revision history and explicit repair work |
| L05 | P1 / performance | Repeated CSV scans, per-player work, repeated model fits and overlapping report regeneration | Import once; partitioned queries; batched features/inference; explicit tuning; cached transform graph |
| L06 | P1 / performance | Core scraper HTTP requests lack timeouts; independent thread sleeps do not cap aggregate traffic | Pooled client, host-wide rate limits, response caps, bounded retries and conditional requests |
| L07 | P0 / security | Weekly flow pushes Phase 1 before later gates; agents use bypass-permission CLI mode; live scripts own Git writes and can report an unchecked push as successful | Separate local computation from a single sealed-artifact publisher; optional editorial without shell/Git authority |

## Improvements beyond bug fixes

These are design requirements, not claims that a deployed vulnerability was demonstrated.

| Area | Improvements to include |
|---|---|
| Performance | Season partitions; projected queries; deterministic materialized aggregates; bounded memory; incremental source/transform manifests; no training during import/refresh; sharded public catalogs; lazy search and validator loading; bounded browser caches; operation-count budgets |
| User experience | Search-first navigation; clear disposal units; exact season filters; shareable filters; accessible sortable tables; comparison with coverage; local watchlists; honest stale/unavailable states; readable mobile summaries; offline/export paths; structured source/method explanations; recovery actions |
| Security | Contained paths and ZIP members; redirect/address checks; sanitized HTML and assets; spreadsheet-safe exports; no private files in releases; CSP tested in production; trusted-local model loading; credential separation; sealed uploads; explicit local live/archive semantics |
| Code quality | One domain registry and feature engine; versioned contracts; typed reset semantics; complete CLI/service composition; test-owned roots/clocks; integration using Python-produced browser data; behavioral fault injection; one current operator manual; migration and rollback rehearsal |

Retain the working strengths: coverage-aware aggregations, explicit source policies, atomic file helpers, runtime browser validation, accessible chart tables, responsive navigation, local watchlist fallback, deterministic export helpers and the legacy regression cases. Rebuild their integration around explicit contracts.
